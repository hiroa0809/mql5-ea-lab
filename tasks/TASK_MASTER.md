- **売買ルールも一意化済み**。`docs/trading_rules.md` を読むこと。**資料（S1/S2）の本文はこの文書に抽出済みなので再取得しない**。資料に無く Claude が決めた箇所は **【一意化】** と明記してあり、そこは変えてよい
- **MT5 の組み込み指標 `iIchimoku()` と `iBands()` は使わない。** 2026-08-05 時点で「これらで足りる」と書いていたが、2026-08-07 の検証で**両方とも否定された**:
  - `iIchimoku()` — 先行スパンのバッファは 26 本先行済みで格納されており、本指標が必要とする「先行させない現在値」は 26 本未来の位置に当たり `CopyBuffer` で取り出せない
  - `iBands()` — **母標準偏差**（n で割る）だが、Matrix Trader は**標本標準偏差**（n−1 で割る）。そのまま使うとバンド幅が 2.47% 狭くなる
  - どちらも**黙って違う値を返す**ため、気づかずに使うと目視確認でズレの原因究明に時間を溶かす。高値・安値・終値から自前算出する（合計数十行）
- **突き合わせの相手は Matrix Trader（USD/JPY 5分足）**。目視確認・検算はすべてこの画面と比べる

### 開発フロー（2026-08-05 合意）

```
0. コスト予算の確認        ← 実装前に必ず通す
1. 要件定義（売買ルールの一意化）
2. 設計書
3. タスク分解 → TASK_MASTER 登録
4. インジケーター実装 → チャートで目視確認
5. EA 実装
6. IS → 検証用 → 最終OOS
```

**ステップ0を先頭に置く理由**: 前回の破棄はロジックではなくコスト前提で決まった。対象銘柄・時間足を決めた時点で往復スプレッドを実測し、「狙う値幅が何 pips で、コストの何倍か」を先に出す。1倍を割るなら実装せずに条件を変える。

> **「保有が長くなるからコスト不利が小さくなる」は取り下げた（2026-08-07・N1b）。** 以前ここに「トレンドフォロー寄りで保有が前回（M15 × 24本＝6時間）より長くなる見込み」と書いていたが、N1b で見積もった R1 の想定保有は **M5 × 10〜60本（50分〜5時間）** で前回とほぼ同じか短い。**優位性は保有時間ではなく獲得値幅（σ ≈ 16.7 pips のスケール）で確保する**必要がある。根拠は `docs/trading_rules.md` §4.3。

**ステップ4に目視を明示する理由**: 成果物は「動いた」ではなく「帯・遅行スパンの見え方が参照資料の図と一致している」こと。ここで認識がずれると後段の数字が全て無意味になる（[[mql5-verification-honesty]]）。

**設計書とタスク分解の順序**: 設計書が先。判定ロジックが確定しないとタスクの粒度が決まらず切り直しになる。「要件定義 ⇄ 設計書」の往復は可。

### 最大のリスク（要件定義で最も時間を使う所）

**スパンモデルもスーパーボリンジャーも、元は裁量判断の補助ツールであり、機械的なエントリールールが一意に決まっていない。** 「遅行スパンがローソクを上抜け」「価格が青帯の上」をどう組み合わせ、どのタイミング（確定足／ザラ場）で発火させるかは実装者が決める部分。ここの決め方で結論が変わる。

→ **要件定義の成果物は「if 文にそのまま落とせる文章」にする。** 曖昧なまま実装すると、負けたときに「ルールが悪いのか実装が悪いのか」を切り分けられなくなる。

### 実装方針（先に決めた設計判断）

- **判定ロジックは `.mqh` に置き、インジケーターと EA の両方から呼ぶ。** EA がカスタムインジケーターをハンドル経由で参照する作りにすると、テスターでの再計算が重くなりバグの切り分けも面倒になる
- `_archive/2026-08-05-legacy/Include/Signals/ISignal.mqh` のインターフェース（`Init` / `Update` / `Entry`）はそのまま流用できる
- **単体で見てから組み合わせる。** 2つを AND で使うのは魅力的だが、前回は単体の赤字が確定しているのに AND 統合を最終目標に据えていた。まず片方ずつ IS にかける
