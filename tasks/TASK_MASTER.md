### 開発フロー（2026-08-05 合意）

```
0. コスト予算の確認        ← 実装前に必ず通す
1. 要件定義（売買ルールの一意化）
2. 設計書
3. タスク分解 → TASK_MASTER 登録
4. インジケーター実装 → チャートで目視確認
5. EA 実装
6. IS → 検証用 → 最終OOS
```

**ステップ0を先頭に置く理由**: 前回の破棄はロジックではなくコスト前提で決まった。対象銘柄・時間足を決めた時点で往復スプレッドを実測し、「狙う値幅が何 pips で、コストの何倍か」を先に出す。1倍を割るなら実装せずに条件を変える。

> **「保有が長くなるからコスト不利が小さくなる」は取り下げた（2026-08-07・N1b）。** 以前ここに「トレンドフォロー寄りで保有が前回（M15 × 24本＝6時間）より長くなる見込み」と書いていたが、N1b で見積もった R1 の想定保有は **M5 × 10〜60本（50分〜5時間）** で前回とほぼ同じか短い。**優位性は保有時間ではなく獲得値幅（σ のスケール）で確保する**必要がある。根拠は `docs/trading_rules.md` §4.3。

**ステップ4に目視を明示する理由**: 成果物は「動いた」ではなく「帯・遅行スパンの見え方が参照資料の図と一致している」こと。ここで認識がずれると後段の数字が全て無意味になる（[[mql5-verification-honesty]]）。

**設計書とタスク分解の順序**: 設計書が先。判定ロジックが確定しないとタスクの粒度が決まらず切り直しになる。「要件定義 ⇄ 設計書」の往復は可。

### 最大のリスク（要件定義で最も時間を使う所）

**スパンモデルもスーパーボリンジャーも、元は裁量判断の補助ツールであり、機械的なエントリールールが一意に決まっていない。** 「遅行スパンがローソクを上抜け」「価格が青帯の上」をどう組み合わせ、どのタイミング（確定足／ザラ場）で発火させるかは実装者が決める部分。ここの決め方で結論が変わる。

→ **要件定義の成果物は「if 文にそのまま落とせる文章」にする。** 曖昧なまま実装すると、負けたときに「ルールが悪いのか実装が悪いのか」を切り分けられなくなる。

### 実装方針（先に決めた設計判断）

- **判定ロジックは `.mqh` に置き、インジケーターと EA の両方から呼ぶ。** EA がカスタムインジケーターをハンドル経由で参照する作りにすると、テスターでの再計算が重くなりバグの切り分けも面倒になる
- ~~`_archive/2026-08-05-legacy/Include/Signals/ISignal.mqh` のインターフェース（`Init` / `Update` / `Entry`）はそのまま流用できる~~ → **初版では使わない**（2026-08-08・N2 の決定7）。ルールが2つの段階で抽象を挟んでも得るものがない。ルール3の形が決まってから必要なら導入する。出典: `docs/implementation_design.md` §1
- **単体で見てから組み合わせる。** 2つを AND で使うのは魅力的だが、前回は単体の赤字が確定しているのに AND 統合を最終目標に据えていた。まず片方ずつ IS にかける

#### 計測ツール `Experts/SpreadProbe.mq5` の使い方（再計測が必要になったとき）

- 売買ロジックを持たない計測専用の EA。テスター以外では `OnInit` で起動を失敗させる（成行注文を出すため）
- **実行時の必須設定**: モデルは **「実際のティックに基づく全ティック」**、遅延は**遅延なし**。モデルを外すと固定スプレッドで埋まり計測が無意味になる。MQL5 にモデルを問い合わせる API が無いため事前に弾けず、事後の警告に頼る作り
- 出力は共有フォルダ `Common\Files` へ `n0_spread_<銘柄>_<時間足>_<実行スタンプ>_trades.csv` と `_summary.csv`。**上書きは起きない**（2026-08-07 に上書き事故を2度起こして対策済み。PR #8）。実行スタンプは `TimeLocal()` ＋ `GetTickCount()` で作るが、**どちらもテスターでは衝突しうる**（前者はシミュレーション時刻、後者は約16分40秒で一周）。最終的な一意性は `FileIsExist` で trades / summary の両方の実在を確認し、埋まっていれば連番を足すことで担保している
- **この計測は IS / 検証用 / 最終OOS の使用回数を消費しない**（戦略の成績ではなくコストの実測のため）。全期間を何度回してよい
- **読む順序**: ①`month` 行で `min` が 0.20 の月が無いか（合成の混入）→ ②`month_check` の `flat_months` → ③`tick_all` の中央値・p99 → ④`hour` 行で時間帯の偏り
- **方式Aと方式Bの一致は「測定の正しさ」の証明にはならない**（2026-08-07 に判明）。遅延なしで走らせると方式Bは定義上その瞬間の気配スプレッドと一致するため、差ゼロは半ばトートロジー。一致が保証するのは**注文→約定→履歴の経路が正しく動き、手数料もスリッページも乗っていないこと**まで
- **遅延あり／なしの比較は実施済み**（2026-08-07）。差 0.002 pips で**レイテンシは無視できる**と確定。同一期間・同一銘柄で、対照群である方式A が完全一致した状態で得た差のため信頼できる
- **本ツールは使い捨てではない。** `docs/backtest_design.md`「通貨ペア分割」で他銘柄のコストを測るとき、最終OOS の終了日を確定するときに再び使う。N0 が済んだからといって捨てない
