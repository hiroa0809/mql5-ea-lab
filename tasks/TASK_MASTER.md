# マスタータスクリスト

## 現在地: 新ロジック「スパンモデル＋スーパーボリンジャー」の着手前（2026-08-05 決定）

3指標（CCI/CMO/RSI）＋プライスアクションの構成は**全て破棄した**。RSI の売買反転・銘柄変更でもプラス収益に届かなかったため、ロジックの手直しではなく作り直しに切り替える。

次に開発するのは**スパンモデルとスーパーボリンジャーを使った EA**。まずインジケーターの実装から入る（2026-08-05 にユーザーが決定。詳細な要件は 2026-08-06 に詰める）。

### 着手前に読む確定事実（再導出禁止）

- **前回の破棄理由は実装ミスではなくコスト前提の誤り**。往復スプレッドを10倍小さく見積もっていた（`USDCNH#` の実測 22 pips に対し、想定していたグロス優位性は 5.06 pips）。出典: `docs/lessons_learned.md`
- 検証の期間分割・回数制限は `docs/backtest_design.md`。**ロジックが変わってもこの設計は変えない**（IS 2018/10〜2022/12 ／ 検証用 2023/01〜2024/10 は2〜3回 ／ 最終OOS 2024/11〜 は1回だけ）
- 旧コードは `_archive/2026-08-05-legacy/`（Git 対象外・ローカルのみ）。**部品取り場**として温存しており、消していない
- **スパンモデル／スーパーボリンジャーの計算実体は MT5 標準関数で取れる**。スパンモデル＝一目均衡表の先行スパン1・2（帯）＋遅行スパン、スーパーボリンジャー＝ボリンジャーバンド＋遅行スパン。`iIchimoku()` と `iBands()` で足り、遅行スパンは終値を26本ずらしたもの。**新しい数式を書く必要はほぼない**
  - ただし上記は一般的な理解であり、**ユーザーが参照している資料の定義で上書きすること**（N1 で確認する）

### 開発フロー（2026-08-05 合意）

```
0. コスト予算の確認        ← 実装前に必ず通す
1. 要件定義（売買ルールの一意化）
2. 設計書
3. タスク分解 → TASK_MASTER 登録
4. インジケーター実装 → チャートで目視確認
5. EA 実装
6. IS → 検証用 → 最終OOS
```

**ステップ0を先頭に置く理由**: 前回の破棄はロジックではなくコスト前提で決まった。対象銘柄・時間足を決めた時点で往復スプレッドを実測し、「狙う値幅が何 pips で、コストの何倍か」を先に出す。1倍を割るなら実装せずに条件を変える。トレンドフォロー寄りで保有が前回（24本＝6時間）より長くなればコスト不利は小さくなる見込みだが、**これは仮説であり実測で確かめる**。

**ステップ4に目視を明示する理由**: 成果物は「動いた」ではなく「帯・遅行スパンの見え方が参照資料の図と一致している」こと。ここで認識がずれると後段の数字が全て無意味になる（[[mql5-verification-honesty]]）。

**設計書とタスク分解の順序**: 設計書が先。判定ロジックが確定しないとタスクの粒度が決まらず切り直しになる。「要件定義 ⇄ 設計書」の往復は可。

### 最大のリスク（要件定義で最も時間を使う所）

**スパンモデルもスーパーボリンジャーも、元は裁量判断の補助ツールであり、機械的なエントリールールが一意に決まっていない。** 「遅行スパンがローソクを上抜け」「価格が青帯の上」をどう組み合わせ、どのタイミング（確定足／ザラ場）で発火させるかは実装者が決める部分。ここの決め方で結論が変わる。

→ **要件定義の成果物は「if 文にそのまま落とせる文章」にする。** 曖昧なまま実装すると、負けたときに「ルールが悪いのか実装が悪いのか」を切り分けられなくなる。

### 実装方針（先に決めた設計判断）

- **判定ロジックは `.mqh` に置き、インジケーターと EA の両方から呼ぶ。** EA がカスタムインジケーターをハンドル経由で参照する作りにすると、テスターでの再計算が重くなりバグの切り分けも面倒になる
- `_archive/2026-08-05-legacy/Include/Signals/ISignal.mqh` のインターフェース（`Init` / `Update` / `Entry`）はそのまま流用できる
- **単体で見てから組み合わせる。** 2つを AND で使うのは魅力的だが、前回は単体の赤字が確定しているのに AND 統合を最終目標に据えていた。まず片方ずつ IS にかける
