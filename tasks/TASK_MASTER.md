### 検証設計（2026-07-27 改訂・カーブフィッティング防止）

**期間分割**

主対象ペアの M15 実データは 2018/10 以降にしか存在しない（それ以前はブローカーに M1 履歴がなく、D1 が M15 として返る合成データ。詳細は下記「データ制約」）。当初の 2016/01 起点は使えないため、利用可能な約7.8年を割り直した。

| 層 | 期間 | 使用回数 | 用途 |
|---|---|---|---|
| IS（開発用） | 2018/10 〜 2022/12（約4.3年） | 無制限 | 閾値調整・試行錯誤。汚れて構わない |
| 検証用 | 2023/01 〜 2024/10（約1.75年） | **2〜3回まで** | IS で決めた設定の確認。落ちたら IS へ戻る |
| 最終OOS | 2024/11 〜 `____/__/__`（実施時に確定） | **1回だけ** | 採用可否の最終判断。見たら調整せず終了 |

- **最終OOS の終了日は実施時に固定する**。「現在」のままだとデータ追加のたびに対象期間が変わり、「1回だけ」という制約と矛盾して結果を再現できない。実施時点のデータ終了日を上表の `____/__/__` に書き込み、**以後データが増えても期間を延ばさない**。
- **最終OOS を見た後に調整して再テストしない**（やった時点で OOS の価値が消える）。
- 「2〜3回」が数えるのは**検証用を見た回数**。IS 側の試行回数は無制限。
- **1回 = 対象条件をまとめて一括実行する単位**。ペア・時間足・パターン・フィルタ ON/OFF を個別に数えない。E4 のように「3パターン × フィルタ ON/OFF × 4ペア」を見る場合、**その全部で1回**と数える。個別カウントにすると上限を即座に超え、検証用が第二の IS に成り下がる。逆に、一括実行した結果を見た後に条件を変えて再実行すれば、それは2回目。
- 往復のたびにパラメータを微調整するのではなく、**ロジックの前提を変えるレベルの変更のときだけ**検証用を使う。2〜3回で通らなければそのアイデアは捨てる。
- IS はボラティリティの高い局面、検証用はレンジ寄りの局面が主。**性格が違うのは汎化を見るうえで好都合**。検証用で落ちたとき「局面が違うから」と言い訳して往復の残弾を使わない。
- Walk-Forward は今回採用しない（パラメータが少なく、目的が「優位性の有無」の判定のため）。EA 仕上げ段階で再検討。

**データ制約（2026-07-27 判明）**

- MT5 はサーバーから **M1 のみ**取得し、全時間足をそこから生成する（[公式ヘルプ](https://www.metatrader5.com/en/terminal/help/algotrading/test_preparation)）。M1 が無い期間は D1 がそのまま返るため、M15 を指定しても**日足でテストされる**。
- 銘柄ウィンドウ → チャートバータブで M1 を指定し「情報呼出」すれば、実データの開始日を確認できる（バー数が営業日数程度なら合成データ）。
- **ヒストリカルデータの削除では解決しない**。標準銘柄の履歴は削除できず、消してもサーバーに無いものは再取得できない。
- 2018/10 以前を使うには Dukascopy 等の外部データをカスタム銘柄へインポートする必要がある。その場合**スプレッドがブローカー実測と乖離する**点に注意（本 EA は薄い優位性を見るためスプレッド影響が大きい）。

**通貨ペア分割（期間分割より強い証拠になりうる）**

- 主対象ペアで優位性を確認し、**開発に使っていない他ペアでも同じ傾向が出るか**で偶然を切り分ける。
- 他ペアと比較する際は**期間を 2018/10 以降に切り揃える**。データ期間が違うまま比べると、差がロジック由来か期間由来か分離できない。
- 銘柄名は本リポジトリに記載しない（公開リポジトリのため）。テスト条件・結果の管理はローカルで行う。

**追加の共通フィルタ（2026-07-26 確定）**

- パターン足が **当日の最高値／最安値を更新していること**を必須条件とする（買いシグナル＝当日安値、売りシグナル＝当日高値）。
- **「その時点までの当日高安」で判定する**（日の 00:00 からパターン足まで）。日が終わってからの確定高安を使うと**未来参照＝リペイント**になりバックテストが実運用と乖離するため。
- 実装は**対象足の時刻**（`iTime(m_symbol, m_tf, shift)`）から日付境界（00:00）を求め、`iBarShift` でその日の開始バーを取り、開始バー〜対象足の範囲を `iHighest`/`iLowest` で判定する。
  - `iTime(_Symbol, PERIOD_D1, 0)` は使わない。`0` は常に「今日」を指すため、履歴バーを検証する際に対象足と無関係な日の境界を拾ってしまう。
- **当日最初の足は除外する**（`count <= 1`）。比較対象が自分しかないと `iLowest`/`iHighest` が必ず自分を返し、フィルタが無効化されるため。
- 副作用として日の後半ほど条件が厳しく、朝方ほど成立しやすい非対称性が出る（仕様上の性質として許容）。

#### E3.5 で確定した事実（2026-07-29 PR #3・再導出禁止）

**逆指値が発動しなかった原因（修正済み）**

- 売りの取消判定が `ask >= invalid` だったため、**パターン足の値幅がスプレッド以下だと予約と同時に取消が成立**し、エントリーの機会自体が発生しなかった（実測: 値幅19ポイント / スプレッド19ポイントで、予約と取消が同一秒）。
- チャートのローソクは **bid 基準**で描かれるため、「安値を割っているのに発動しない」ように見えた。取消判定を **bid 基準へ変更**して見た目と一致させた。
- **売りの損切りにはスプレッドを加算する**（`pat_high + spread + buffer`）。パターン足の高安は bid 基準だが、売りポジションの損切りは **ask で発動**するため、加算しないとスプレッド分だけ手前で狩られる。買いの損切りは bid 発動のため**加算しない**（非対称は意図的）。

**チャート上の × 印は理由の判別に使えない**

- 描画価格が呼び出し元で変わる（逆側ブレイク＝`invalid` の高さ / 期限切れ＝`trigger` の高さ）。色（赤=逆側ブレイク / 灰=期限切れ）でしか区別できず、位置から読み取れない。
- **原因調査には「逆指値の予約・発動・取消をログ出力する」を ON にする**。予約・発動・取消・発注の実数値（trigger / invalid / bid / ask / 残り本数 / entry / sl / tp）が出る。本番テストでは OFF。

**テスターのログの読み方**

- EA の `Print` 出力は**エージェント側**のログに出る: `%APPDATA%\MetaQuotes\Tester\<ID>\Agent-127.0.0.1-3000\logs\`。ターミナル側（`Terminal\<ID>\Tester\logs\`）にはテスト開始・データ同期しか出ない。
- 文字コードは **UTF-16LE**。`Get-Content -Encoding Unicode` では読めず `[System.Text.Encoding]::Unicode.GetString()` が必要。
- **テスト実行中はログがフラッシュされない**。停止するまで最新分は書き出されない。実行中のファイルは掴まれているため `FileShare.ReadWrite` で開く。

**決済ロジック（E5 で本決定するまでの暫定）**

- 「N本経過でクローズする」で ON/OFF 可能。「利確を使う(損切り幅のN倍)」を追加し、**利確 = 損切り幅 × N**（損切り幅にスプレッドとバッファを含むため N=1.0 なら勝率50%で±0）。
- 両方 OFF だと決済手段が損切りのみになり、`OnInit` が警告を出す（エラーにはしない）。
- **利確ロジックの実地確認は未実施**。ストップレベル補正の動作のみ確認済み（1,067件の発注で `Invalid stops` ゼロ、押し戻しにより実測比率が 0.067〜0.133 に分散＝指定値 0.1 から乖離）。**E4 の前に、実用的な倍率（1.0 等）で意図どおり決済されるか目視確認すること**。

**スプレッドの扱い（重要）**

- テスターの「全ティック」モードが使うのは **M1 バーに記録されたスプレッド代表値**で、実運用より狭いのが通常。時間帯による変動も大きい（同一銘柄で 2〜39 ポイントの開きを実測）。
- 本 EA は「トータルマイナス回避」という薄い優位性を見るため、**スプレッドを甘く見積もると結論が逆転する**。IS ではテスター設定でスプレッドを実測より広めの固定値に上書きして回すことを推奨。

## 運用知見メモ

- **CodeRabbit の再レビューは短時間に連発しない**（無料プランのレビュー回数制限。上限到達で約25分待ちが発生）。指摘はまとめて1回の push で対応する（2026-07-26 PR #1 で遭遇）
- **CodeRabbit は増分レビュー方式で、レビュー済みコミットは再レビューしない**（2026-07-26 PR #2 で確認）。`@coderabbitai review` は公式コマンドだが、応答は `Action performed / Review finished` を返しつつ**新規指摘はゼロ**になる（bot 自身が "does not re-review already reviewed commits" と明記）。修正後コードの全体レビューが欲しければ**新しいコミットを push する**しかない。なお `gh pr checks` は PR 単位で最新状態を返すため、新コミットにチェックが無いと**古い成功状態を拾う**。判定は `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` でコミット単位に確認する
- **コンパイル判定は `Result:` 行を読む**。MetaEditor の終了コードは成功／失敗どちらでも同じで当てにならない
- **セッション区切りごとにブランチを main へ統合する**（`fin` ステップ3.5）。統合せず枝を切り続けると、いつか main から切って先祖返りする（過去の事故）
- **`gh pr checks` は state だけで判断しない**（2026-07-29 PR #3 で遭遇）。レート制限で**レビューが走らなかった場合も `state=SUCCESS` になる**（description が `Review rate limited`）。`Review completed` と読み違えるため、**description まで確認する**。
- **レート制限の解除後、自動レビューは走らない**。制限中に来た push を後から処理しないため、`@coderabbitai review` のコメントで**手動起動が必要**。待ち時間は制限コメント本文に「Next review available in: N minutes」と明記される。
- **プランは Pro Plus でも回数制限がある**（無料プラン限定ではない）。直近のレビュー頻度が上位5%に達すると制限が適応的に厳しくなる。
- **ユーザーへの操作説明では、ソースの変数名ではなくテスターのパラメータ画面に出る日本語表示名を使う**（例: `InpTPRatio` ではなく「利確 ＝ 損切り幅 × N」）。変数名は画面に出ないため解読の手間をかけさせる。
