# 実装設計書 — スパンモデル / スーパーボリンジャー

> 売買ルールは `docs/trading_rules.md`、計算定義は `docs/indicator_spec.md`。**本書はそれらを繰り返さない。**
> 本書が扱うのは「どのファイルに何を置き、どの入力で切り替え、どう執行するか」。
> 作成 2026-08-08（N2）。

## 1. ファイル構成

同じ計算をインジケーターと EA の両方が使うため、共通部分を `.mqh` に置いて両方から読み込む。2回書くと片方だけ直したときに食い違い、「チャートは合っているのにバックテストがおかしい」という切り分け困難な状態になる。

```text
Include\Signals\
  SuperBollinger.mqh   … センターライン・σ の計算 ＋ ルール1の判定
  SpanModel.mqh        … スパンA/B・遅行線の計算 ＋ ルール2の判定

Indicators\
  SuperBollinger.mq5   … チャート描画（N4 の目視確認用）
  SpanModel.mq5

Experts\
  EaSpanBollinger.mq5  … ルール1／ルール2 を input で選んで売買
```

**指標ごとに1本、計2本に分ける。** ルール1はスーパーボリンジャーだけ、ルール2はスパンモデルだけを使うので依存が自然に分かれる。`TASK_MASTER.md` の N4 が「一度に両方作らない」と決めており、1指標＝1ファイルならその作業順がそのままファイル単位になる。ルール3では両方を読み込む。

**計算と判定は同じファイルに置く。** インジケーターは描画に計算、シグナル矢印に判定が要る。EA も両方要る。利用者が両方を使う以上、分ける理由がない。

**`ISignal.mqh` のインターフェース（`Init`/`Update`/`Entry`）は使わない。** ルールが2つの段階で抽象を挟んでも得るものがない。ルール3の形が決まってから必要なら導入する（`TASK_MASTER.md`「先回りして汎用テンプレート化はしない」）。`TASK_MASTER.md` の流用候補にあった「そのまま流用できる」の記述は 2026-08-08 に取り消し済み。

### 銘柄・時間足

**`_Symbol` / `_Period` を使い、input にしない。** テスターの設定がそのまま反映され、ハードコーディングも避けられる（`docs/backtest_design.md`「選択可能にする項目」の意図を満たす）。ルール3の上位足だけは input で持つ。

### 必要な履歴本数

`OnInit` で不足を弾く。

**入力値から計算する。固定値を書かない**（期間はすべて input なので、変えた瞬間に固定値が嘘になる）。

```text
ルール1: InpR1_Period + InpR1_LagBars + max(InpR1_SqueezeBars, InpR1_ExpandBars) + 2
ルール2: max(InpR2_Tenkan, InpR2_Kijun, InpR2_SpanB) + InpR2_LagBars + InpR2_SlopeBars + 2
```

既定値では ルール1 = 65、ルール2 = 85。ルール1で最も深く遡るのは①で、膠着を見る最も古い足の帯を求めるのに `Period + LagBars + SqueezeBars`（既定 63）本を使う。式はそれに判定足と余裕を足した形。

> **ルール2に `InpR2_Tenkan` を含める**（2026-08-08・PR #10 のレビュー）。当初 `max(InpR2_Kijun, InpR2_SpanB)` と書いていたが、転換線の期間も計算に使う以上、外すと転換線を一番大きくしたときに不足を検出できない。既定値（9 < 52）では結果は変わらない。

## 2. 入力パラメータ

表示名は日本語にする（`docs/lessons_learned.md`）。`①②③④` の番号は `trading_rules.md` の条件番号と対応させ、診断出力を読んだときに即座に照合できるようにする。

| `InpLots` | 0.10 | ロット |
| `InpMagic` | 20260808 | マジックナンバー |
| `InpReverseOnOpposite` | true | 反対シグナルでドテンする |

### ルール1: スーパーボリンジャー

| 変数 | 既定 | 表示名 |
|---|---|---|
| `InpR1_Enable` | true | ルール1を使う |
| `InpR1_Period` | 21 | 期間（センターラインとσ） |
| `InpR1_LagBars` | 21 | 遅行線の本数 |
| `InpR1_UseSqueeze` | true | ①膠着を条件に入れる |
| `InpR1_SqueezeBars` | 21 | ①膠着とみなす本数（この本数ぶん帯の内側） |
| `InpR1_SigmaMult` | 3.0 | ①③で使うσの倍数 |
| `InpR1_UseLag` | true | ②遅行線の陽転/陰転を条件に入れる |
| `InpR1_UseExpand` | true | ④バンド幅の拡大を条件に入れる |

③（遅行スパンの帯突破）は引き金なので ON/OFF を持たない。外すとルールが成立しない。`InpR1_SigmaMult` は①と③の両方に効く（同じ帯を物差しにするため）。

### 診断

| 変数 | 既定 | 表示名 |
|---|---|---|
| `InpPrintCounters` | true | 条件別の成立回数を出力する |

### 表示名の付け方

方向に依存する言葉を使わない。「平らでも上向きとみなす」「+1σ 割れで手仕舞う」は買い目線であり、売りのとき意味が通らない。

| 避ける | 使う |
|---|---|
| ④平らでも上向きとみなす | ④判定にイコールを許可する |
| ②遅行線の陽転を条件に入れる | ②遅行線の陽転/陰転を条件に入れる |
| ③終値が青スパンの上を条件に入れる | ③終値と青スパンの位置関係を条件に入れる |

## 3. 執行の仕様

### エントリー

- 判定は確定足（`shift = 1`）のみ。ザラ場では判定しない（`trading_rules.md` §2.1）
- 発注は**次の足の始値で成行**
- **建玉は常に1つまで。** 保有中に同じ方向のシグナルが出ても無視する。積み増すと平均建値・建玉ごとの損切りが絡み、可変ロットを不採用にした理由（検証が複雑になる）とぶつかる

### 決済

- 手仕舞い条件（下記のX1系）は確定足で判定し、**次の足の始値で成行**
- **損切りだけは例外で、足の途中で発動する。** サーバー側の損切り注文なので、確定足を待たずに約定する。`trading_rules.md` §2.1 の「ザラ場判定はしない」は EA の**判定**についての決まりで、ブローカー側の逆指値の執行はこれに当たらない
- ルール1: 終値が 1σ の内側へ戻ったら手仕舞う
- ルール2: 雲の色が反転したら手仕舞う（＋ input で遅行線の反転も）

### ドテン

**ドテンが実際に起きるのはルール2だけ。** 2つのルールで事情がまったく違う。

| | 手仕舞い条件 | 反対シグナル | 関係 |
|---|---|---|---|
| ルール2（買い保有中） | 雲が赤になる | 雲が赤へ転換した足 | **同じ出来事**。毎回ドテンになる |
| ルール1（買い保有中） | 終値が +1σ を割る | 終値が −1σ を割る **＋ ①膠着 ＋ ④拡大** | **ほぼ無関係**。下記 |

ルール1の売りは −1σ 突破だけでなく①膠着（直前21本が ±1σ 内）も要求する。買いを持っていたということは直前がトレンドなので①は成立せず、**手仕舞いだけが起きて反対建玉は入らないのが通常**。ドテンは例外的にしか発生しない。

同じ足で揃った場合は、次足始値で**決済と反対建玉を同時に行う**。`InpReverseOnOpposite` を false にすると決済のみ。**この入力が効くのは実質ルール2**。

### 損切り

**既定は使わない（`InpR1_UseSL` / `InpR2_UseSL` = false）。** 手仕舞い条件かドテンで抜けるのが基本設計であり、損切りの有無はバックテストで比較して決める。損切りは資料に記載がなく（`trading_rules.md` §4.2）、閾値を調整できるつまみを増やすほど学習期間の成績は実力以上に良く出る。

使う場合は**注文にサーバー側の損切り価格を付ける**。EA がティックを監視しない（§2.1 と整合する）、EA が停止しても効く、建玉の向きに応じた気配（買いは Bid、売りは Ask）を MT5 が自動で見る、の3点による。σ は建玉時の値を固定するため、損切り価格は建玉時に確定する。

> **売り側は Bid ではなく Ask。** 買い建玉は売って閉じるので Bid、売り建玉は買って閉じるので Ask を見る。`trading_rules.md` §4.2 の「売りは上下反転」はここを省いており、そのまま実装するとスプレッドのぶん売り側の損切りが甘くなる。サーバー側の損切りにすればこの誤りは起きない。

ブローカーの最小距離（`SYMBOL_TRADE_STOPS_LEVEL`）を下回る場合は、**最小距離まで広げて建てる**。見送りにすると σ が小さい場面（＝ルール1が狙う膠着明け）の取引だけが抜け落ち、成績が実態とずれる。広げた回数は診断に出す。

## 4. 診断出力

`InpPrintCounters` が true のとき、テスト終了時（`OnDeinit`）に条件ごとの成立回数を出力する。

```text
[ルール1] ①膠着 812 / ②遅行線 3204 / ③±1σ突破 451 / ④拡大 5130
          4つ揃った 7   買い 4 / 売り 3
          損切りを最小距離まで広げた 0
```

**取引ゼロで終わったときに、どの条件で止まったかを切り分けるため。** 前回の破棄は「ルールが悪いのか実装が悪いのか分けられない」状態が尾を引いた。実装は数行で済む。

各条件は**単独で**数える（他の条件の成否と無関係にカウントする）。そうしないと「①が原因で②が数えられていない」といった連鎖が起き、切り分けにならない。

## 5. N2 で決めたこと

| # | 決定 | 理由 |
|---|---|---|
| 1 | 条件別の成立回数を出力する | 取引ゼロのとき切り分けられるようにする |
| 2 | 遅行線は厳格版（高値・安値と比較）のみ実装 | 緩い版（終値比較）では「絡む」という中間状態が作れず、資料が p13・p15 でレンジ判定に使っている状態が消える |
| 3 | ~~条件①を p15 の定義（±1σ 内推移）に置き換え~~ → **2026-08-09 に破棄**。①と③をどちらも「遅行スパンと帯の距離」で測る | p15 の定義は、同じ21本から作った帯と自分を比べる形なので何も測っていなかった。値動きを20倍にしても成立率が変わらない（`trading_rules.md` §3.3） |
| 4 | 長期スパンの傾きは `>` を既定、イコール許可を input で | 長期スパンは階段状で平らな期間が長い。ただし実装前に決めず、診断カウンタを見てから調整する |
| 5 | 建玉は1つまで／反対シグナルではドテン | 積み増しは検証を複雑にする。ドテンは資料の「雲の色に従う」考え方に沿う |
| 6 | 損切りは既定 OFF、バックテストで比較 | 手仕舞い条件で抜けるのが基本設計。つまみを増やすと学習期間の成績が実力以上に出る |
| 7 | `.mqh` は指標ごとに2本 | 依存が自然に分かれ、N4 の「一度に両方作らない」作業順と一致する |

## 6. 初版で実装しないもの

| 項目 | 理由 |
|---|---|
| 手仕舞いに p13 の3条件を全部使う版 | バンド幅の「収束」の定義が要る。資料に定義がなく、決めるのは必要になってから |
| 遅行線の緩い版（終値比較） | 決定2。条件②の成立回数を見て、少なすぎたら足す |
| ②を遷移として扱う版（`InpLagAsTrigger`） | ②は状態のまま実装する。遷移する条件が2つあると同じ足で揃わない。診断カウンタで②の成立回数が過大（＝フィルタとして効いていない）と分かってから考える |
| ルール3（統合） | ルール1／ルール2 の単体成績を見てから（`trading_rules.md` §6） |
