## 破棄した試行から得た一般則（2026-08-02 〜 2026-08-05）

3指標（CCI/CMO/RSI）＋プライスアクションの構成は**全て破棄した**。実装が誤っていたのではなく、前提が誤っていた。同じ轍を踏まないための一般則:

- **pips / points / 桁数は銘柄ごとに実データで確認する**。前提のスプレッドを **10 倍小さく見積もっていた**ことが全ての原因だった。価格の小数桁の分布を数えれば判別できる（`USDCNH#` は4桁＝1 point = 1 pip）。**単位換算が絡む比較は、絶対価格など換算不要な量に落として検算する**。
- **スプレッドはテスターの約定データから直接実測できる**。重複保有を許すと同一時刻に buy と sell の約定が並ぶことがあり、その価格差が ask−bid になる（2026-08-02 に177件で実測・中央値 0.00220 CNH ≒ 22 pips）。**新しいロジックに着手する前に、対象銘柄の往復コストを実測して優位性の予算と比較する**。
- **「グロスでプラス」は優位性の証拠にならない**。全12,064セルの 80.1%（5分足では 98.2%）でグロスがプラスだった。時間足が短いほど強く（5m 98% → 4h 61%）、極値直後の気配の戻りを拾う系統効果にすぎず、スプレッドを跨ぐ実運用では取れない。**判定は必ずネットで行う**。
- **多数の条件を試すなら、ノイズの天井を先に見積もる**。12,000通り試せば t 値 4.0 程度まではノイズが到達する。段階1スクリーニング（t値≥4.0 かつ 取引数≥200）は通過ゼロ、最大 t は 3.46（取引数4件）だった。
- **選別条件に OOS の結果を混ぜない**。前プロジェクトの研究は `oos_survivor = (net_is>0) & (net_oos>0) & ...` と OOS の結果を選別に使っており、OOS になっていなかった。
- **バックテスト結果が事前検証と乖離したら、まず「検証時と条件が同一か」を照合する**。指標・閾値が同じでも、決済・時間足・銘柄・コスト前提のどれか1つが違えば結論は覆る。原因を推定する前に条件照合を先に行う。
- **事前チェックが、実装前には存在し得ない数字を要求していないか確かめる**（2026-08-08 追記）。上の教訓から作った「ステップ0: コスト予算の確認」は、コスト（市場が決める＝事前に測れる）と獲得値幅（自分のルールが決める＝実装後にしか出ない）を同じ欄で要求していた。**埋められない欄は空欄で残らず、手近な値で埋まる**。実際 σ の1本読みが代表値に格上げされ、根拠の無い「事前ゲート通過」を生んだ。**戒めから作った装置ほど、そこに書かれた数字は疑われにくい**。
- **引き継ぎでは「ロジック」だけでなく「採用構成」を必ず持ち込む**。時間足・決済ルール・スプレッド前提・銘柄が欠落したまま引き継ぎ、未検証の仮置き決済でバックテストを回して原因究明に時間を要した。**確定事項は参照先リポジトリ任せにせず、本リポジトリ側に転記する**。

## MQL5 / MetaTrader

- **コンパイル判定は `Result:` 行を読む**。MetaEditor の終了コードは成功／失敗どちらでも同じで当てにならない。
- **テスターは前回の入力値を `Profiles\Tester\<EA名>.set` に保持する**。enum の選択肢を削除すると古い値が残り、**無言で取引0**になる（2026-08-02 実測）。取引0を見たら、まずコードより先に `.set` の値を疑う。新しい EA でも**未対応の入力値が来たら `OnInit` で起動を失敗させる**こと。
- **他ブローカーの MetaEditor も同じ手順で使える**（本プロジェクトでは XM のみ）。データフォルダ ID: FXGT MT5 Terminal = `EB299DF3DF8E2F9A1C0723943438596E` / OANDA MetaTrader 5 = `EE0304F13905552AE0B5EAEFB04866EB`。XM の ID は `.claude/CLAUDE.md` のジャンクション手順にある。
- **ユーザーへの操作説明では、ソースの変数名ではなくテスターのパラメータ画面に出る日本語表示名を使う**（例: `InpTPRatio` ではなく「利確 ＝ 損切り幅 × N」）。変数名は画面に出ないため解読の手間をかけさせる。

## CodeRabbit / PR 運用

- **短時間に再レビューを連発しない**（レビュー回数制限。上限到達で約25分待ち）。指摘はまとめて1回の push で対応する。
- **プランは Pro Plus でも回数制限がある**（無料プラン限定ではない）。直近のレビュー頻度が上位5%に達すると制限が適応的に厳しくなる。
- **増分レビュー方式で、レビュー済みコミットは再レビューしない**。`@coderabbitai review` は自動レビューが停止している場合にのみ有効。修正後コードの全体レビューが欲しければ**新しいコミットを push する**。
- **レート制限の解除後、自動レビューは遡って走らない**。制限中に来た push は `@coderabbitai review` で**手動起動が必要**。待ち時間は制限コメント本文の「Next review available in: N minutes」に明記される。
- **`gh pr checks` は state だけで判断しない**。レート制限で**レビューが走らなかった場合も `state=SUCCESS` になる**（description が `Review rate limited`）。**description まで確認する**。また `gh pr checks` は PR 単位で最新状態を返すため、新コミットにチェックが無いと**古い成功状態を拾う**。コミット単位の判定は `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` で行う。
